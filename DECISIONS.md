# Decisions

One line each: problem, choice, why.

- Studio tools are zero-dependency Node ESM, so a clean clone needs only Node 20+ (Playwright is added in Phase 3 for the playtester).
- Phase 2: all three agents share one working directory (the studio). Switch Console runs every session in the agent's directory as-is, with no git worktrees (console/agents/architecture/data-model.md), so files hand off through the folder.
- Phase 2: on Windows, Console 0.40.1 won't create Claude Code agents from a template ("SDK sessions require a POSIX SSH execution host"), but its New agent dialog does. So the three agents were created by hand with the template's instructions. The template marks them `allow_existing: true`: on Windows you pick "Existing agent" and it creates only the room, Discord channel and kickoff; on Mac/Linux it creates everything.
- Phase 3 (early): playtest.mjs runs game time on Playwright's fake clock (seed 42), so checks are deterministic and a 60 s game takes a few real seconds; it uses a private server for the test and starts serve.mjs on :8080 for humans if it is down.
- Phase 3: public links via GitHub Pages on the public repo jatinvats123/jam-studio-arcade (the studio's origin, main branch, root, with .nojekyll). publish.mjs pushes, then polls the new version's URL for a 200 for at most 90 s (not 120 s) because Claude Code's Bash tool times out at 2 minutes; local links stay as the fallback (JAM_LOCAL=1 or no remote).
- Phase 3: each game gets a short link play/<slug>/ (a redirect page that build-arcade regenerates to point at the latest version). The starter already had the viewport meta and auto touch buttons, so no change was needed for phones.
- Phase 3: screenshot in chat. Agent ops have no attachment operation (attachments are media routes in the runtime, not an op the agent can call), so the builder's live post ends with the Pages URL of screenshot.png, which Discord unfurls into an image.
- Phase 3: native approval. Switch core relays a Claude Code session's permission requests to the bridge as "Permission needed" cards (approval_requests; who may answer = who may address the agent). The studio's .claude/settings.json has an ask rule for `node tools/publish.mjs`, so publishing raises a card a human must accept. Verified live 4 PM Nov 5: the card "Permission needed · request A1, 🚀 Publish Cat vs Cucumbers v1 to the public arcade" with Allow once / Allow for this session / Decline appeared in the builder's Discord thread; a button click from the web client didn't register, the typed answer "A1 1" did. The designer's "approve" for the plan stays a chat reply (#1131: reactions don't reach agents).
- Phase 3: Console restarts an agent's session (claude --agent <name> --resume) when its instructions are saved, but the resumed session keeps its old conversation, so it acts on stale memory (the builder skipped a re-publish as "already live" and posted old credits). `!reset-all-agents` in the room clears context; run it before demo takes.
- Phase 3: agent mentions wake agents, so the builder's chatty "@jam-designer specs it" made the designer propose an unrequested v2. Builder may mention agents only in handoff lines; designer starts a v<N+1> only when a human asks.
- Phase 4: a room per game. The designer calls `create_room_from_yaml` with templates/jam-game-room.template.yaml after a human approves the plan in the lobby (not before), so rooms exist only for approved games and the template's kickoff is the builder handoff ("@jam-builder build <slug> v1"). Approval stays in the lobby; building, testing, changes and bugs happen in #game-<slug>. Switch records each room in a run, so Console shows lobby -> game rooms as a tree.
- Phase 4: no room group. A room template has no group key and no agent op files an existing room into a group (only `create_room(group_name=…)` can), and switching to `create_room` would lose the kickoff. Links (lobby <-> game "game: <Title>"/"lobby", original <-> remix "remixed as"/"remix of") and the run tree give the organisation instead.
- Phase 4: game rooms get aliases from the template (@designer, @builder, @tester). The existing lobby gets them once with `!set-alias @jam-designer @designer` etc.
- Phase 4: jam-playtester addressing is now `anyone` (was owner-agents) so a friend can report "@tester bug: …" directly. Its instructions limit it to bug reports from humans and test requests from the builder.
- Phase 4: bug repros are saved as games/<slug>/v<N>/repro-<k>.json and replayed by every later playtest as hard checks; earlier versions' scenario.json are replayed as advisory checks only, because a "## vN changes" block can change old behaviour on purpose. Scenario + repros run first, advisory replays last and only if the 85 s budget allows. `--only <file>` runs one repro and writes nothing.
- Phase 4: hotfix credit lives in the hotfix version's NOTES.md first bullet ("- hotfix: <bug> (bug hunter: <name>)"), which the builder may write; build-arcade reads it. This keeps the "who writes where" rules (nobody but the designer touches GAME_SPEC.md).
- Phase 4: the builder posts the lobby "now playing" note by connect_to_room(lobby) → post_message → connect_to_room(back), since post_message only targets the connected room.
- Phase 4: agents stalled overnight because Claude Code on this PC was signed out (`claude auth status` → loggedIn false, empty tokens); Console-managed agents then answer "Sign in on the execution machine with claude auth login". Fix: `claude auth login` in a normal terminal, then `!reset-all-agents` in each stuck room. Worth a line in the blog's gotchas.
- Phase 4: scenarios gained a `{"log":"name"}` step (prints state, never a check) and the playtester explores with a scratch probe.json via `--only`, because the first playtester filled scenario.json with `"expect":"false"` probes and went quiet. Its instructions now require a posted verdict after at most 3 runs.
- Phase 4: publishing one game swept another room's half-built version onto the arcade (`git add games` + "latest folder wins"). Now publish.mjs writes games/<slug>/v<N>/PUBLISHED and commits only games/<slug>; build-arcade lists only marked versions. Existing published versions were marked once by hand.
- Phase 4: an advisory replay cut short by the 85 s budget now counts as skipped, not failed (it made a correct hotfix look like a FAIL).
- Phase 4: playwright pinned to exactly 1.64.1: 1.65.0 was published with playwright-core@1.65.0 missing from npm, so `^1.64.1` broke fresh installs on Nov 6.
- Phase 4: agents see Discord usernames, not display names, so credits and "bug hunter" show billusanda5808 unless a human states their display name (the designer then uses it). Open; for demo takes, say the display name once.
- Nov 6 (A): Codex's Windows sandbox runs commands as a restricted user that can't read %LOCALAPPDATA%\ms-playwright, so Playwright failed with `spawn EPERM` (and Codex blamed the game). Choice: the studio keeps its own Chromium in .browsers/ (gitignored; setup installs it there via PLAYWRIGHT_BROWSERS_PATH; playtest.mjs uses it when present). Verified: sandboxed `codex exec --sandbox workspace-write` ran the full playtest (19 checks, 61 fps). Running Codex with the sandbox off was not an option.
- Nov 6 (A): the playtester slot runs on Codex by default (`tester_provider: [codex, claude]`, so Claude Code where Codex is missing): the model that builds never grades its own work. On Windows the agent is hand-made as jam-playtester-gpt; `scripts/live-instructions.mjs --tester jam-playtester-gpt` renames every handoff to it, and the designer passes it to the game-room template (`playtester` input), so @tester points to it. Fallback: regenerate without --tester and re-paste designer + builder.
- Nov 6 (A): playtest.json records `runner` ("GPT · Codex" / "Claude") from env vars each CLI sets (CODEX_* checked first: Codex inherits Claude's env when nested), so no new agent duty.
- Nov 6 (A): tool failures are not game bugs: the playtester posts "PLAYTEST BLOCKED: <error>" with no mention instead of "fix".
- Nov 6 (B): "How this game was made" pages (games/<slug>/index.html, tools/making-of.mjs) are built by build-arcade from existing files only. Two optional spec fields feed them: `approved_by` (designer adds it on approval) and "## v<N> changes (asked by …)". publish commits every game's page, so they stay current.
- Nov 6 (C): explain-it mode needs the builder's addressing = anyone; its instructions limit humans to "explain" (anything else is pointed to the designer). Kickoff lines say "ask the builder" with no @, because an agent's mention would wake the builder.
- Nov 6: couldn't set `cli_auth_credentials_store = "file"` in ~/.codex/config.toml from Claude (auto mode blocks persistent config edits); auth.json already exists, so it's a user step only if Console's Codex session fails on login (#1048).
- Nov 6 (A, live): Console's Codex provider showed "CLI not installed" and its Install button did nothing visible; `npm i -g @openai/codex@0.166.0` put codex on PATH and Console then showed "Codex · Signed in" (ChatGPT login, no Pro needed). jam-playtester-gpt (Codex, studio dir, addressing Anyone) ran `test comet-dash v1` in a Console direct chat: real playtest, 18/19 checks, 61 fps, report posted. Its one ❌ (A4 star pickup) was its own scenario (the cat died before reaching a star), so the run was reverted with git to keep the published 19/19 report. The builder's addressing is a custom rule (users: any, agents: my agents), because Console's dropdown wouldn't switch to Anyone.
- Nov 6: moving @tester to another agent needs `!remove-alias @tester` first (set-alias refuses a used alias).
- U1 (Nov 6): Switch enforces who directs the builder. Switch core's addressing policy (core/switch_core/addressing.py) is a list of allow-rules over rooms/groups/users/agents; once a rule exists everything else is denied and Switch posts its own refusal ("You're not permitted to direct messages to me in this room…"). Approval cards follow the same policy (who may answer = who may address). Choice: builder = Console custom rule {users: Me + approvers' chat usernames, agents: My agents}; the template says `owner-agents` because a template can't name individual people (only owner / owner-agents / anyone / anyone_in).
- U1: explain-it mode moved from the builder to the designer (addressing anyone), so humans who aren't approvers lose nothing when the builder is locked. Kickoffs say "ask the designer" with no @.
- U1: playtester stays `anyone` so any friend can say "bug: …"; "only agents may request test" is prompt-enforced, because addressing judges the sender, not the message.
- U1: identity = Switch sender id. Agents get `sender` + `sender_name` per message from read_context (and ids from list_participants). studio/people.json maps sender id -> {name, username}; only the designer writes it, asking once "What name should I credit you as?". Credits, approved_by, "asked by" and bug-hunter names come from it; plan approvals count only from senders whose participant type is user. people.json is gitignored (it holds chat ids), so it never reaches the public arcade.
- U2 (Nov 6): offline proof. `npm run verify` (scripts/verify.mjs) and `npm run eval` (scripts/eval-playtest.mjs) build throwaway studios from studio-kit/ + examples/games/ inside jam-room/.verify/ (gitignored), so the studio tools resolve Playwright from jam-room/node_modules and a clean clone needs only `npm ci` + `npx playwright install chromium`. No Discord, Switch, credentials or git pushes. Shared helpers: scripts/lib/temp-studio.mjs.
- U2: examples/games/ holds the 3 real games (cat-vs-cucumbers, penguin-slide v1+v2 hotfix, comet-dash) copied unedited from the live studio, so verify replays what agents actually wrote in Discord (spec, code, scenario.json, repro-1.json).
- U2: playtest.mjs skips starting the :8080 studio server when JAM_NO_SERVE=1 (set by verify/eval), so test runs leave no stray processes.
- U2: the eval plants one bug of each of 7 kinds (collision off, score frozen, game over unreachable, a control ignored, console error on start, fps killer, restart broken) per sample game with exact-anchor text mutations (scripts/eval/mutate.mjs replaceOnce throws if an anchor isn't found exactly once, so a mutant can't silently be a clean copy). Mutants are written as bugs a builder could plausibly make, never tailored to the checks. Misses are reported, not hidden.
- U2: CI (.github/workflows/verify.yml, ubuntu, Node 20) runs verify + eval on every push and uploads docs/eval.md; the README badge goes live once jam-room is pushed (not pushed yet: needs the user's OK). The bundled sample playtest.json files predate the `runner` field, so the cross-vendor claim is listed under live evidence in JUDGING.md, not as an offline check.
- Nov 6 (CI): the first GitHub CI run failed comet-dash A4 (star pickup) though it passes on this PC. Cause: playtest.mjs installed Playwright's fake clock without pausing it, so real time leaked into game time and a slower machine saw ~30 ms more (the cat was 21 px further right and missed the star). Choice: `clock.pauseAt(1000)` before loading the game, so only scenario waits move time and results are the same on every machine. A busy loop that waits on performance.now() would then freeze the page forever, so each clock advance is capped at 20 s real time and a frozen game becomes a FAIL ("game froze …") instead of a hang.
- Nov 6 (CI, cont.): with the clock paused, the eval missed 2 "control ignored" mutants. Not the clock: under 3 parallel playtests the "key X has an effect" check was skipped by the time budget (<40 s left), and a skip counted as a pass. Choice: the key checks now run right after start() (before the scenario) with no time-budget skip; they cost one page and 600 ms of game time per key.
- Nov 6 (CI, part 3): the paused clock was still not machine-independent: run 42182338923 (same code as the green run) failed comet-dash A4 again, and 8 parallel local runs ended A4 on frame 497 or 498. Cause: Playwright replays the paused clock into a new page at the *real* time the pause happened (pauseAt(1000) is not kept), so each page's load time depended on machine speed, and fake animation frames fire on a fixed 16 ms grid, so the game loop's fixed-step phase moved by a step. Choice: freshPage() fast-forwards to the next 16 ms grid point at least 1 s ahead, giving one frame with a long gap; the starter's fixed-step loop clamps it and drops its leftover time, so every run starts from the same phase (8/8 parallel runs then gave identical states). That exposed comet-dash's A4 as luck: its 600 ms right-press parked the cat at x 865, 11 px outside the star at x 833 that the old phase happened to catch. Choice: the sample scenario now presses 550 ms (any 520-590 ms works) and checks for +10 within a 4 s window (survival alone adds ~4), synced to the live studio. The fast-forward goes through the same 20 s freeze guard as every other clock move: a game that busy-waits on performance.now() otherwise hung the playtest there (penguin fps-killer timed out once).
- U8 (Nov 6): "Caught on camera". clip.mjs uses the same player as playtest.mjs (browser, paused fake clock on the 16 ms grid, seed 42 and the scenario runner moved unchanged into studio-kit/tools/player.mjs; verify 17/17 and eval 21/21, 0 false FAILs right after the move), so a clip is the test run with a camera. Only the clip page seeds Math.random (mulberry32, seed 42) for cosmetics; playtest checks are untouched. Two runs give the same sha256 (a verify claim).
- U8: GIFs, not video, because Discord plays GIFs inline. gifenc 1.0.3 (MIT, pure JS) pinned in both package.json files. 480x270 per side, one frame per 80 ms of game time; a repro longer than 10 s becomes a time-lapse (penguin repro-1 holds 30 s, so 4x speed, 7.6 s, 1.34 MB); over 5 MB, half the frames, once. Labels use drawn icons, not emoji glyphs (CI has no emoji font).
- U8: correction to Phase 3. Console 0.40 agents do have send_attachment and download_attachment, and an addressed message's attachments arrive already downloaded. The builder keeps its Pages screenshot link; the playtester posts the clips. A clip never delays the handoff, and a failed clip is one "(clip failed: …)" line.
- U8: the README's hero fix-1.gif was made offline from the agent-written repro-1.json (penguin-slide v1 vs v2) and committed to examples/ and the live studio; live clips come from the playtester. A clip written after the builder's publish commit goes live with that game's next publish (clip ~20 s vs a human tapping Allow, so rare).
